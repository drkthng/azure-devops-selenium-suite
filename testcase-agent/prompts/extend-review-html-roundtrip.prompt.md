**The round trip.** We send the reviewer the generated HTML file. They open it, mark up the cases, click one button, and send us back a file. That returned file is the whole feedback channel — there is no server, no shared folder and no JSON for them to handle.

What they can record: per test case, a status of *ready for automation*, *needs changes*, or *not applicable*, with **unreviewed as the distinct starting state** — a plain checkbox cannot tell "not looked at yet" apart from "looked at and rejected", and that difference is the entire point of the review gate. Also per case, a free-text comment; and per step, a comment that is collapsed until used.

They cannot edit the text of a case or a step, and this is deliberate — do not add it. A rewritten step would have to be merged back into `out/*.md` by hand, with no diff and no record of the original, and the `.md` is the authored record that the ADO importer parses and codegen reads. A comment saying what should change costs the reviewer the same typing and leaves us applying the edit where git sees it.

**How the file comes back.** Add a "Save my review" button that rebuilds the complete HTML document with the current state written into the markup — both reflected into the elements' attributes so a reopened file visibly shows the reviewer's answers, and embedded once as a machine-readable `<script type="application/json">` block — then downloads it as `<basename>.review-<reviewer>.html`. Reopening a returned file must restore everything from that block, so a reviewer can stop halfway and continue later, and so we can read their comments sitting next to the steps they refer to.

Do not rely on the browser's own "Save page as" for any of this, and do not tell the reviewer to use it. Checkbox and textarea state lives in DOM properties, not in the markup, so a browser save returns a file that looks complete and contains none of their work — silent data loss, which is worse than an error. Because reviewers will reflexively press Ctrl+S anyway, intercept it and run the save action instead. Also warn on page close while there are unsaved changes.

The button is fixed in the bottom-right corner so it stays visible while scrolling, and its label carries the state: the number of unsaved changes, going quiet once saved. Add bottom padding to the page so it never covers the last test case, and hide it in `@media print` with the other controls. Keep it to one restrained control — the page must still read as a document, not as an application. Ask the reviewer for their name before the first save and keep it in the file.

**What the payload must contain**, because we have to be able to trust it later: the source file name, a SHA-256 of the source `.md` as it was when rendered, the render timestamp, the reviewer name, and per case the stable case id, the case title, the status and the comments. The hash is not optional — it is what tells us whether a returned review still applies to the `out/` file we have, or whether the case was regenerated in the meantime and the review is stale. Store the title alongside the id so a human can re-match by hand if an id ever fails to line up.

This needs a genuinely stable per-case id. Build this in the same run as the export, not later: both ends share one payload format, and splitting them across two runs is how the two ends drift apart.
