Build a Python script in `tools/render-review-html/` that renders our generated test-case files from `out/` into a single self-contained HTML page for human review.

Who this is for: the QA colleagues who review the drafts. They do not work in VS Code and would rather be handed a document. This HTML file is the compromise, so it has to behave like one: open by double-clicking the file, readable offline with no install, no server and no network access, and printable to PDF when someone wants paper. Optimise for skimming — fifteen or so test cases in one file, each collapsed to a single readable line until the reviewer opens it. Markdown in a text editor is what we are replacing; do not reproduce it.

Read these first, they define the input: `style/testcase-schema.md` (the structure every `out/` file follows — the fields, and how steps are represented as action + optional-expected pairs) and one real file in `out/`. Derive the parse from those two, do not assume a structure. `tools/ado-importer/` already parses the same files; if its parser can be imported and reused as-is, do that. Do not refactor the working importer to make it fit — if reuse would mean changing it, write a separate parse for the renderer and put the case for extracting one shared parser module into a fenced proposal block at the end of your reply, so I can decide.

**This is a read-only view.** The script reads `out/` and writes `review/<same-basename>.html`. It never writes to `out/`, never modifies a `.md`, and the HTML has no editing, no approval marks, no comment fields and no state of any kind. The `.md` file stays the single authored artefact — it is what the importer parses, what codegen reads, and what git tracks. The HTML is derived and thrown away on every re-run.

**Fidelity is the hard rule.** The renderer displays what the file says, verbatim. It never rewrites, reflows, summarises, corrects or omits text. All of our markers — `[UNVERIFIED: …]`, `[OCR UNCLEAR: …]`, `[NEEDS SCREENSHOT: …]`, `[HUMAN CALL: …]` — must survive into the output word for word and be visually obvious, since they are the whole point of the review. If the parser meets a section it does not recognise, render it verbatim inside a clearly flagged "not recognised" block; never drop it. A renderer that silently swallows content is worse than no renderer, because the gap is invisible to the reviewer.

Layout: one card per test case, collapsed by default. The collapsed header line carries title, area path, step count, and a badge with the number of open markers in that case — that line alone should be enough to decide whether to open it. Expanded, show preconditions and the source/coverage information, then the steps as a numbered two-column table of action and expected result, with the expected-result cell visibly empty where our file gives none. Above the cards put a sticky bar with the file name, the total case count, the total marker count, expand-all / collapse-all, a text filter over titles and step text, and a toggle for "only cases with open markers". Give each case a stable anchor id so a reviewer can link a colleague straight to one case. Do not require a schema change for this — derive the anchor from the case title.

Make it look like a document, not an application: black on white, one column, generous line height, a readable measure of roughly A4 width, a sober system font stack. No dark theme, no app chrome, no animation. Under `@media print`, expand every case, hide the controls, and avoid page breaks inside a case or inside a step row.

Practicalities: Python standard library only — no pip install, no markdown library, and inline every bit of CSS and JavaScript so the file is genuinely single-file. No CDN, no web fonts, no external requests of any kind; assume the machine is offline and that the file will be forwarded by mail or Teams and opened somewhere else. If you conclude this cannot be done without a third-party package, stop and tell me before writing anything. Write all UI labels in the language the `out/` files are written in, since the reviewers read those. Take a single input file path as a command-line argument like the importer does, plus an `--all` flag to render everything in `out/`, and print the path of each file written.

Before it prints success, the script must verify it did not lose anything: count the test cases and the markers in the source `.md`, count them again in the generated HTML, and fail loudly with both numbers when they disagree rather than writing a file that looks complete.

After the first successful run, show me: the counts it verified, the path to open, and a list of anything defined in `style/testcase-schema.md` that you chose not to display, with your reason.
